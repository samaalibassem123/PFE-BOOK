\section{Introduction}
This chapter presents \textbf{Sprint 0}, dedicated to system analysis and design. During this sprint, the objective was not to implement functional modules yet, but to understand the source systems, define user needs, identify the required data scope, and prepare the main design artifacts that would guide the following development sprints.

The work carried out in this sprint focused on four complementary axes: identifying the actors and their access scope, modeling the main use cases, analyzing the source systems and the ETL-oriented data structure, and defining the global architecture of the solution.

\section{Sprint Design}
Sprint 0 design aimed to transform a business problem into a structured technical solution. The design effort started with user and access analysis, then moved to source-system exploration, and finally to the high-level architecture that would orient ETL and application development.

\subsection{Global System Architecture}

The architecture starts by extracting data from \textbf{BioTime (PostgreSQL)} and \textbf{EasyProject (MySQL)} with \textbf{SQLAlchemy}. The data is then transformed and loaded into the main application database.

On top of this unified database, the backend uses \textbf{FastAPI}, \textbf{Alembic}, and \textbf{SQLAlchemy}. It exposes endpoints consumed by a frontend built with \textbf{React}, \textbf{Tailwind CSS}, and \textbf{shadcn/ui}.

\subsection{Actors and Access Scope}
The platform has three main actors. Each actor has a clear role in the system:

\begin{itemize}[noitemsep]
	\item \textbf{Administrator (Admin)}: manages accounts and project assignment. The Admin creates accounts, approves accounts, and assigns projects to Project Managers.
	\item \textbf{Human Resources (HR)}: works on company-wide HR follow-up. HR can view employees, employees' clock-in/out records, and employees' leave information.
	\item \textbf{Project Manager}: works at team level. The Project Manager can view members, assigned projects, and team attendance.
\end{itemize}

\subsection{Functional Scope of the Sprint}
During this sprint, the design effort focused on clarifying what each actor must be able to do before implementation begins. This early clarification reduced ambiguity and helped prepare later module decomposition.

\begin{itemize}[noitemsep]
	\item The \textbf{Administrator} scope was defined around account lifecycle control and project-to-manager assignment.
	\item The \textbf{HR} scope was defined around organization-wide consultation of employee, attendance, and leave information.
	\item The \textbf{Project Manager} scope was restricted to assigned projects and their related members and attendance indicators.
\end{itemize}

\section{Sprint Outcomes}
At the end of Sprint 0, the main outcome was a complete analysis and design baseline that structured the rest of the project. Even though no final user-facing module was delivered yet, this sprint produced the essential functional and technical artifacts used in the following iterations.

\subsection{Main Deliverables of Sprint 0}
\begin{itemize}[noitemsep]
	\item Defined the three main actors of the system and clarified their access boundaries.
	\item Produced the global use case diagram and the textual description of major use cases.
	\item Explored the BioTime and EasyProject schemas and selected the relevant tables for integration.
	\item Designed SQL views to simplify extraction and harmonization during ETL processing.
	\item Prepared the initial unified PostgreSQL target view of the data model.
	\item Established the class diagram, physical ERD, and end-to-end global architecture.
\end{itemize}

\subsection{Sprint 0 Contribution to the Next Sprints}
Sprint 0 served as the foundation for all later work. The ETL sprint relied on the selected tables, source views, and target schema defined here. The authentication and business-module sprints also reused the actor definitions, access scope, and architecture decisions established during this initial analysis and design phase.
